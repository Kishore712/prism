# Proposal: Guarded Prism Recovery After an Offline Close

**Status: Proposed for a material security-boundary decision; not authorized, implemented, or deployed. This proposal does not establish that automatic recovery is safe.**

## Evidence and current behavior

Three delayed outages have been observed. In the first two, `tailscaled` logged `PollNetMap` EOF/reset at 2026-09-28 02:15:06.868Z and 06:28:52.761Z; the watchdog recorded offline about 0.287 and 0.347 seconds later. The third was recorded at 2026-09-29 19:07:18.936Z with no logged precursor in the preceding 10 minutes. `category=offline` means the watchdog observed `Self.Online=false`; the source of that status is unknown. All watchdogs intentionally fail closed on a single false sample.

In the third event, service exit was logged at 19:07:18.945Z and first active state at 20:33:12.278Z, an observed interval of 1h25m53.33s from service main-process exit to the next recorded active state, not an established period of service downtime or HTTPS availability duration. No logged `Online=true` sample exists before the manual restart. Same-PID Shields Up and netmap-return logs do not prove `Self.Online` recovery. At a 21:42 UTC point-in-time check, the VM and all three units were running, Tailnet was `Running/Online`, and Shields Up was false while serving; no changes were reported. See the [sanitized validation record](validation/m2-browser-active-disconnect.json).

The approved offline-close rule preserves `tailscaled` when local shielding is confirmed and leaves Prism stopped. The earlier proposal's phrase “unshielding remains an explicit operator action” describes historical intent: an operator start runs `ExecStart=serve`, which starts and binds the private HTTPS listener behind Shields Up; `ExecStartPost=open` then checks HTTPS locally, clears Shields Up, and rechecks. Tailscale's control/data-plane and out-of-sync documents provide context, not a diagnosis or proof of recovery safety ([control and data planes](https://tailscale.com/docs/concepts/control-data-planes), [“not in map” poll message](https://tailscale.com/docs/reference/messages/client/not-in-map-poll)).

## Proposed decision and sequence

Consider a separate root-only recovery path after the existing offline fail-close. The installed watchdog records a category but has no durable unique offline-event ID; implementation must create one and fail closed if it cannot persist it. Permit at most one attempt per durable event, excluding manual operator stops. Any unknown, stale, failed, contradictory, or unauditable condition denies recovery. The proposed sequence is ordered; later gates do not substitute for earlier ones:

1. **Confirm fail-close settled.** Verify the offline event identity and category, the Prism service is stopped, and its cgroup is drained. Require Tailnet `Running/Online`, exact pinned installation and host identities, exact safe preferences, and `ShieldsUp=true`. Collect fresh paired status/preference samples at a bounded cadence for a proposed 60 seconds on a monotonic clock. Reset the interval on any failed, false, changed, or inconsistent sample, then perform a final recheck. This is sampled evidence, not proof of continuous health.
2. **Inspect workload state under the database lock.** With the service stopped, acquire the existing shared `server.lock` (or a demonstrated equivalent trusted handoff). Verify database integrity and that every queued, running, or uncertain run count is zero. Verify the Kata namespace is empty. Persist and audit recovery intent and consumption of this unique event before starting any unit; if either record cannot be made durable, deny. Release the lock only through a defined trusted handoff before starting the watchdog. A consumed event is never retried automatically.
3. **Start and verify the watchdog.** Start the watchdog explicitly through that handoff. Verify reconciliation completed and health using the documented health signals; a healthy socket alone is insufficient. Reacquire `server.lock` through the trusted handoff and repeat the complete status/database/namespace check: database integrity and all queued/running/uncertain counts, empty namespace, Tailnet `Running/Online`, pinned identity/preferences, Shields Up, and service stopped/drained. Release/reacquire again only through a defined systemd/lock handoff at the Prism-start boundary, and recheck every condition there. Deny if atomic exclusion or any handoff cannot be shown.
4. **Start Prism through the pinned systemd unit.** The normal `ExecStart=serve` starts and binds the private HTTPS listener while Shields Up is still enabled. Then `ExecStartPost=open` checks HTTPS locally, clears Shields Up, and rechecks. The recovery state helper must not directly change Shields Up. This post-start unshielding is the expected effect of the separately authorized private-service start option, not a claim that Shields Up remains true while serving. Verify private readiness and the expected service/watchdog state.

A new recovery lock by itself cannot serialize with operator starts, resolver actions, or systemd lifecycle jobs. Any implementation must integrate with systemd and the existing `server.lock` (or a demonstrated equivalent trusted handoff), release and reacquire locks in a defined order, and recheck every relevant condition at each handoff. Since the service itself uses `server.lock`, the protocol must not hold that lock across a start that needs it. It must prove atomic exclusion from manual starts and resolver activity; if it cannot show this, recovery is denied. Lock contention or ambiguous ownership also denies.

If start or post-start readiness fails, explicitly stop Prism, verify the close path completed, verify inbound shielding is restored, and verify the service cgroup is drained. If any of those checks fail, use the existing emergency fail-closed procedure and report recovery as unresolved; do not retry automatically. Audit every gate, handoff, event consumption, start, and outcome in the root-private audit trail without secrets. Audit failure before a start denies it; if outcome auditing fails after start, explicitly stop Prism, verify close/shield/cgroup state, and report the recovery unresolved.

This changes the current no-automatic-recovery rule and can cause the ordinary private-service start path to bind the listener behind Shields Up, then have `ExecStartPost=open` check HTTPS locally, clear Shields Up, and recheck. It requires a separate owner decision that explicitly accepts those effects before implementation or host use.

## Manual-only alternative

Keep the current behavior: after offline close, Prism stays stopped. An operator verifies strict online state, pinned identity and preferences, and shielding before starting the service; the normal `ExecStart=serve` binds the private listener behind Shields Up, after which `ExecStartPost=open` checks HTTPS locally, clears Shields Up, and rechecks. This accepts potentially longer downtime without a new automatic start path.

## Acceptance criteria if separately authorized

- **Positive:** Demonstrate ordered gate execution, fresh paired samples and final recheck; fail-close completion; locked, intact database with zero queued/running/uncertain runs; empty namespace; durable event consumption before unit start; watchdog reconciliation and health; full repeat check; proven lock handoffs/exclusion; and one pinned-unit start where `ExecStart=serve` binds HTTPS behind Shields Up, then `ExecStartPost=open` checks HTTPS locally, clears Shields Up, and rechecks. Audit contains no secrets and no credentials, grants, or model configuration change.
- **Denial:** Independently invalidate each gate, including event replay or manual stop, service/cgroup not drained, any nonzero run state, corrupt/unreadable database, nonempty namespace, tailnet or preference drift, Shields Up false, failed/unstable sample, unhealthy or unreconciled watchdog, audit failure, and lock conflict or unproven atomic handoff. Prism must not start.
- **Fault:** Inject watchdog start/reconciliation failure, Prism start failure, HTTPS self-check failure, audit failure, lock handoff race, and operator/resolver contention. Failed post-start checks must stop Prism and verify close, shielding, and cgroup drain; otherwise invoke emergency fail-close. No repeated attempt may consume the same event.
- **Regression:** Preserve single-sample fail-close, the approved shield-preserving offline close, existing manual recovery, and no public exposure.

## Non-goals and limits

This proposal does not change the single-false-sample watchdog policy, explain the outages, prove host or Tailnet health between samples, or establish a hard uptime/recovery guarantee. It authorizes no implementation, host change, credentials/grants/model changes, or public access. It does not establish safety or pilot readiness; `pilot_ready` remains false unless separately established by its required evidence.
