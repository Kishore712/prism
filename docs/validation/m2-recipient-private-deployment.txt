# Sanitized private deployment checkpoint

Date: 2026-09-22/23

This note records the bounded private deployment checkpoint. It omits project,
account, VM, hostname, client, secret, key, URL, and operation identifiers.

- A dedicated Tailscale HTTPS certificate was issued. One dedicated Google Web
  OAuth client was registered. No real browser OIDC flow was run.
- On the target VM in `us-central1-b`, a first scheduling update omitted
  `maxRunDuration` and `terminationTime` and returned Operation DONE, but did
  not clear either field. A second `setScheduling` explicitly set both fields
  to null; a fresh independent GET confirmed both were absent.
- The earlier public-key-only KEY boot passed by generating an RSA-4096 key
  and returning only its public key; that boot did not install the app. APP
  source-delivery attempts f, g, i, and j did not install it: g received
  metadata HTTP 503, i exhausted retries with an ambiguous outcome, and j
  received three network exceptions for the same request. The subsequent
  one-boot source-delivery path failed before app installation: the controller
  reported `protected_vm_drift` before sending chunks, and the guest receiver
  raised `BlockingIOError` on its serial device before READY. The user rejected
  automatic timeout shutdown.
- The authorized temporary access pivot used Google IAP and OS Login SSH. A
  first project-level key add failed because the project was missing and was
  fully rolled back. A second attempt succeeded through IAP; host-key
  trust-on-first-use was independently checked, then strict host-key checking
  was enabled. The guest-reported VM identity matched the API result.
- The fixed compressed payload and wrapper were copied. The first wrapper
  rejected the inventory layout at `stage_inventory`, before mutation. After
  correcting the location under high review, one fixed install passed.
- Independent guest checks verified `installed.json`, a complete ledger, all
  six payload-part SHA-256 values, all 29 source-file SHA-256 values, Python
  3.13.5 in the virtual environment, and successful imports of Prism,
  Authlib, FastAPI, and Uvicorn. The Python archive did not have an
  independently pinned SHA-256; that remains a supply-chain verification
  limitation.
- The install did not start the application: `service_started=false` and
  `model_calls=0`. No OIDC secret was installed, no live login or browser
  check occurred, and no model or Kata integration was exercised.
- Before the successful fixed install, a small non-executable metadata probe
  had demonstrated attach/remove writes only; its independent follow-up found
  the VM STOPPED with its original four metadata controls and no ingress.
  Earlier independent i/j checks likewise found STOPPED state, the original
  four controls, no startup metadata, and no ingress; a later check after more
  than ten minutes remained clean with no matching operation, and request
  state was retained.
- The initial temporary IAP access path was fully revoked: SSH sessions were
  closed, the OS Login key profile was cleared, the dedicated firewall rule and network tag
  were deleted, and the IAP API was disabled. The target VM remains RUNNING;
  both scheduling limits are absent, old startup and idle-timeout metadata
  are cleaned, the original four metadata controls remain, there is no service account, Shielded VM is enabled, and effective
  ingress is zero on both VMs.
- This is an app-install checkpoint, not order-4 acceptance. OIDC service
  configuration and HTTPS serving remain to be deployed and independently
  reviewed. Real browser identity, model, and Kata checks require separate
  review before execution. Keep the VM running for that next reviewed step.

This is a preparation checkpoint, not order-4 acceptance. Historical pass/fail
records are unchanged.
