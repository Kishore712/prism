## Product security requirements

The following rules implement the project's stated boundaries. They are review requirements, not claims that controls already exist.

### Authorization and approvals

- Deny by default. Bind every operation to authenticated recipient, session, approved version, current grant revision, host policy, expiry, and remaining budget. Apply the same checks to tools, direct APIs, search, streaming, reconnects, artifacts, and downloads. An opaque ID is not permission.
- Derive identity and authorization context on the server. Do not trust client-supplied roles, history, tool outcomes, provider conversation IDs, or approval flags. Use configured OIDC and recipient-bound invitations; no anonymous fallback or home-grown password system in P0.
- Store owner approvals server-side and bind them to the exact proposed increment, recipient, version, action/resource, parameters where applicable, expiry, and budget. An agent rationale, framework approval object, or permission request is not a grant. Approval changes require reauthorization before any later execution.
- Do not add repeated owner prompts for actions already covered by a valid grant. New scope remains inactive until specifically approved; adding content requires a new reviewed version.

These requirements apply the deny-default and per-request checking principles in [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html). Framework integration must also respect PydanticAI's documented [approval trust boundary](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/).

### Context, files, and agent memory

- Materialize explicit selections into an immutable candidate, then approve the exact bytes and executable/environment definitions. A live source mount is not a snapshot. P0's conservative importer rejects symlinks, hard links, special files, and automatic archive extraction; any later support requires dedicated boundary tests.
- Keep excluded files, history, memory, metadata, and credentials out of recipient prompts, filesystems, tools, caches, and indexes. Build retrieval only from permitted material. Do not retrieve privately and filter afterward.
- Start a fresh collaborator session and isolate mutable state between recipients and sessions. Do not attach to the owner's unrestricted agent. Scope reductions must invalidate affected history, summaries, caches, in-flight outputs, and provider-side conversation state before reuse.
- Treat runtime-readable material as potentially disclosed. Source writes are denied; recipient writes use separate bounded storage. File snapshots, dependency environments, active processes, and process memory are distinct resources.
- Imported instructions and tool results cannot change policy. Prompt filtering, content screening, and model refusals are defense-in-depth measures, not the enforcement boundary.

See [OWASP AI Agent Security](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) for scoped tools and isolated context, and [OWASP Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) for indirect-injection threats and defense limitations. Apply the project-specific restrictions above rather than copying illustrative snippets as a complete security design.

### Execution, network, and budgets

- P0 tools submit fixed approved executables with typed, bounded parameters. Prefer structured APIs; never interpolate model/user text into shell commands. Validate option semantics as well as syntax, executable identity, and input scope. No generic shell or arbitrary code evaluation in the trusted service.
- Execute project code only in the validated sandbox. Never expose a home directory, source workspace, SSH agent, host control socket, personal environment, or inherited credential. Worker/runtime management access belongs to trusted host components, not the collaborator or model.
- Deny task-network access by default. Where a later design enables networking, enforce destination and operation restrictions outside the model, including redirects, DNS changes, loopback, metadata services, and private-network targets. Model calls use a separate approved adapter and route.
- Enforce finite CPU, memory, process, writable-storage, log/output, time, concurrency, and aggregate budgets. Reserve budgets atomically before dispatch. Bound model iterations and retries. SDK usage counters alone do not enforce aggregate cost ceilings.
- A missing runtime capability blocks activation. Container-only synthetic development mode is not a validated private-pilot mode. Validate the reference Linux VM-backed runtime or obtain approval for a justified alternative; never silently downgrade isolation.
- Use durable job state and idempotency. Do not automatically retry uncertain side effects. On revoke/expiry, block further access and output, cancel queued/running work, expire host leases, and verify termination of the entire job group. Previously disclosed data cannot be recalled.

The command rules follow [OWASP OS Command Injection Defense](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html). [OWASP Docker Security](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) informs container configuration, but does not establish the stronger runtime properties required by Prism's [security invariants](docs/product-design.md#security-invariants).

### Outputs, credentials, and records

- Validate citation targets, versions, ranges, and access before rendering. Label original findings, new run results, and interpretations distinctly. Valid references do not prove an answer's correctness.
- Treat generated output as untrusted: no active scripts, automatic external-resource loads, unsafe file paths, or automatic execution of downloaded artifacts. Use bounded safe errors that do not expose hidden source locations or resource existence.
- Keep model-provider credentials in trusted configuration. Before enabling external inference, disclose destination and sent data categories. Local execution is not local inference. Do not silently change providers, enable hosted memory, or export traces containing content.
- Minimize local security records and make optional research measurement disableable. Do not collect hidden model reasoning or unrelated private content. Explain owner visibility and retention to collaborators; track access revocation, execution termination, and data deletion separately.
